# init fixtures

What `rulebearing init --dry-run` proposes for a test bed in [the manifest](../manifest.yaml), committed as `<owner>__<name>/rulebearing.yaml` so that a change in discovery is a reviewable diff ([plan 0001, Step 16](../../docs/plans/pending/0001-wave-1-typescript-parity.md#step-16-init-1f); [plan 0002, Step 15](../../docs/plans/pending/0002-wave-2-dotnet-python-element-rules.md#215-step-15-greenfield-init-proof-the-nightly-tables-upstream-offers-second-maintainer-2i)). Regenerate with [`run.sh`](run.sh) over checkouts at the manifest SHAs, with the .NET solution built by the row's `build` command. Each file names the SHA it came from and the summary line of the run, which is the cruise with the proposal exiting 0. The baseline entries are replaced by their count per rule: they are the test bed's findings, not init's discovery.

Regenerate the greenfield fixtures on a case-sensitive file system, as the nightly's Linux runner is: MSBuild imports `Directory.Build.props` by exact name only on one, so a checkout on a case-insensitive volume (the macOS default) builds differently and leaves a different number of references unresolved (semantic-kernel 2,351 against 1,879, autogen 1,381 against 1,228).

The two greenfield beds are the wave 2 proof ([design § Test beds](../../docs/artifacts/design.md#test-beds-open-source-repositories-to-validate-against), item 2): every rule live, and every current finding baselined. The nightly ([`greenfield.sh`](../greenfield.sh)) clones each at its SHA, builds it, writes the full proposal with `init`, cruises it back (exit 0 is the pass), and regenerates the fixture beside the committed one; a difference fails the row.

## Framework presets

`run.sh --preset <name>` runs `init --dry-run --preset <name>` and writes `<owner>__<name>/preset-<name>.yaml` beside the proposal without it: the proof that a framework preset ([presets/frameworks](../../presets/frameworks/README.md)) yields a configuration that passes or is baselined on a real repository ([plan 0003, Step 11](../../docs/plans/pending/0003-wave-3-operations-surface-inner-loop.md#23-steps-for-sub-wave-3c-presets-lifecycle-fields-snapshot-and-changelog), which names `testbeds/fixtures/`; they live here, beside the init fixtures of the same beds, because they are init fixtures and `run.sh` writes both). Each file's second line is the verdict: the cruise with the proposal exits 0, with the count of findings baselined. For a greenfield row the nightly regenerates each of its `preset-<name>.yaml` files with the proposal and fails when one changes ([greenfield.sh](../greenfield.sh)); an oracle row's preset fixture, such as langfuse's, is regenerated by hand with `run.sh --preset`.
