## Context

For Python, resolution is the whole job: absolute imports against the discovered roots, relative imports against the file's package, then the standard library, then installed distributions, then `unresolved`. Which modules are standard library depends on the interpreter version the repository targets.

## Decision

- `rb-extract-python` parses with `ruff_python_parser` (MIT) and resolves imports against roots discovered from `pyproject.toml`, the `src/` layout and a `setup.cfg` fallback.
- `languages.python.version` selects a bundled snapshot of `sys.stdlib_module_names` per supported interpreter version; the list is regenerated by a script in `rb-extract-python` and committed.
- `dependencyTypes` for Python are `local`, `stdlib`, `site`, `type-only` (a `TYPE_CHECKING`-guarded import), `dynamic` (a literal `importlib.import_module` or `__import__`), `unresolved`.
- The code layer records classes, functions, methods, decorators, bases, `@property`, `@staticmethod`, `@classmethod`, `@dataclass`, and underscore visibility.
- `__init__.py` stands for its package as the module identity. Default excludes are `.venv/`, `site-packages/`, `__pycache__/`, and `*.pyi` unless `--stubs`.
- import-linter contracts map one to one onto rule kinds (`forbidden`, `layers`, `independence`, `protected`, `acyclic siblings`, `ignore_imports`), and `import import-linter` performs that mapping.

## Consequences

- The Python oracle repositories' contracts must reproduce exactly; that is the wave 2 exit criterion for Python.
- A new Python release means a new stdlib snapshot and a pull request, nothing more.

## Alternatives considered

- **Shelling out to an interpreter.** Rejected: non-hermetic and version-dependent.
- **grimp as a library.** Rejected: it would require Python at run time.
