Rulebearing Guard Cookbook

Every guard a team writes by hand today, a cycle check, a dead-code sweep, a licence gate, a layer fence, a budget that only falls, is one entry in the rule file. This page shows the entry for each, in the shapes the rule language accepts.

0 to 255the count of error violations, from a gating reporter
2the run cannot be trusted: a vacuous rule, a missing budget, unreadable input
3the configuration is invalid: an unknown key, a missing decision token, a predicate the language cannot answer

The file

One native file groups rules by family. Every dependency-cruiser key is legal at the same place with the same meaning; the native format adds keys and renames none. Families marked wave 2 are specified in the design and planned in docs/plans/pending/0002; the rest land with wave 1.

rulebearing.yaml
$schema: https://benbahrenburg.github.io/rulebearing/schema/config-v1.json
extends: rulebearing:recommended        # six quality rules, every one with a fix
defines: {}                             # values read from JSON, used as ${name} in any pattern
languages:
  typescript: { tsConfig: { fileName: tsconfig.json } }

rules:
  dependencies:                         # dependency-cruiser's rule set, whole
    forbidden: []                       #   an edge or a module that matches is a violation
    allowed: []                         #   an edge no entry covers is a violation
    required: []                        #   a module that does not import (or reach) a target is a violation
  layers: []                            # shorthand: one forbidden rule per lower-to-higher pair
  independence: []                      # shorthand: one $1 fence between sibling folders
  ratchets: []                          # a count of edges that may only fall, against a budget file
  elements: []                          # ArchUnitNET's select / where / should            (wave 2)
  slices: []                            # notDependOnEachOther, beFreeOfCycles              (wave 2)
  diagrams: []                          # adhereTo: a PlantUML component diagram            (wave 2)

options:
  doNotFollow: { path: node_modules }
  knownViolations: []                   # the baseline; each entry carries expires and owner

allowEmpty: []                          # rules allowed to match nothing, by name
Two formats, one model. A .dependency-cruiser.js that works with dependency-cruiser 18.2.0 runs here unchanged. rulebearing config convert moves it to the native format losslessly, and the reverse direction prints what it dropped. Reference: docs/config.md.

Anatomy of a rule

Every family shares the same metadata. The four fields dependency-cruiser does not have (fix, examples, owner, expires) are what explain, err-long and the agent reporter print.

rules.dependencies.forbidden[]
- name: domain-depends-on-nothing
  comment: "Domain is the centre of the template. plan:0005-guard-catalogue"
  fix: "Move the shared type into src/domain, or invert the edge so application code depends on domain."
  severity: error
  from: { path: "^src/domain/" }
  to:   { path: "^src/(application|infrastructure|web)/" }
  examples:
    forbidden: ["src/domain/order.ts -> src/application/create-order.ts"]
    allowed:   ["src/application/create-order.ts -> src/domain/order.ts"]
  owner: "@platform-team"
  expires: null
name
Stable, kebab-case. The baseline, the violation id and explain key on it.
comment
The why, with a decision token adr:NNNN or plan:<slug>. --require-comment-token makes a rule without one exit 3.
fix
The imperative to follow when the rule fires. config lint flags a fix that restates the name.
severity
error counts toward the exit code. warn and info are reported. ignore is silent.
from / to
Matchers on the resolved path. A capture in from.path is $1 to $9 in to, escaped so it matches only itself.
examples
Edges rulebearing test builds into a synthetic graph. A rule cannot merge without proof it fires.
owner
Who answers for the rule.
expires
A date, for a temporary exception. The run fails the day after.
allowEmpty
Opts the rule out of liveness. Without it, a rule whose from matches nothing is vacuous and exits 2.

Code quality guards

Facts about the graph itself: cycles, orphans, imports that resolve to nothing, licences, coupling. The first four ship in rulebearing:recommended; write your own only to narrow or extend them. A rule you name the same as a preset rule replaces the attributes it names.

No cycles, and type-only edges do not count

forbiddenerrorwave 1

Tarjan's strongly connected components find the cycle and the report enumerates its path. scope: folder applies the same rule to folders instead of files.

rules.dependencies.forbidden[]
- name: no-circular
  comment: "A module on a cycle cannot be changed, tested or moved on its own. plan:0005-guard-catalogue"
  fix: "Break the cycle: move the shared code into a module both sides import, or invert one edge behind an interface. Type-only imports do not count."
  severity: error
  from: {}
  to: { circular: true, dependencyTypesNot: [type-only] }

- name: no-folder-cycles
  comment: "Folders are the units people reason about; a cycle between them hides in file-level green. plan:0005-guard-catalogue"
  fix: "Move the file that closes the folder cycle into the folder it really belongs to."
  severity: warn
  scope: folder
  from: { path: "^src/" }
  to: { circular: true }

No dead modules, no imports that resolve to nothing

forbiddenwarnerrorwave 1

An orphan imports nothing and is imported by nothing. Entry points and configuration files are orphans by design, so the rule excludes them by path rather than going quiet.

rules.dependencies.forbidden[]
- name: no-orphans
  comment: "A module nothing imports and that imports nothing is usually dead code. plan:0005-guard-catalogue"
  fix: "Delete the module, import it from where it belongs, or add its path to this rule's from.pathNot if it is an entry point."
  severity: warn
  from:
    orphan: true
    pathNot:
      - "(^|/)\\.[^/]+\\.(js|cjs|mjs|ts|cts|mts|json)$"     # dotfiles
      - "\\.d\\.(c|m)?ts$"                                    # type declarations
      - "(^|/)(page|layout|route|loading|error)\\.tsx?$"      # framework entry files by convention
      - "(^|/)(vite|vitest|eslint|prettier|next)\\.config\\.(js|cjs|mjs|ts)$"
  to: {}

- name: not-to-unresolvable
  comment: "An import that resolves to nothing fails at run time or hides a missing package. plan:0005-guard-catalogue"
  fix: "Fix the specifier, or add the package to package.json; for a path alias, check tsConfig and enhancedResolveOptions."
  severity: error
  from: {}
  to: { couldNotResolve: true }

Tests and dev-only packages never leak into production code

forbiddenerrorwave 1

Two edges to forbid: production code importing a test helper, and production code importing a package that only exists in devDependencies. Matchers hit the resolved path, so a path alias cannot dodge the fence.

rules.dependencies.forbidden[]
- name: production-never-imports-tests
  comment: "A test helper in a production bundle ships mocks and fixtures to users. plan:0005-guard-catalogue"
  fix: "Move the shared helper into src/ as ordinary code, or keep the import inside the test tree."
  severity: error
  from: { path: "^src/", pathNot: ["\\.(test|spec)\\.[jt]sx?$", "(^|/)__tests__/", "(^|/)test-utils/"] }
  to:   { path: ["\\.(test|spec)\\.[jt]sx?$", "(^|/)__tests__/", "(^|/)test-utils/", "(^|/)__mocks__/"] }
  examples:
    forbidden: ["src/orders/service.ts -> src/orders/__tests__/fixtures.ts"]
    allowed:   ["src/orders/service.test.ts -> src/orders/__tests__/fixtures.ts"]

- name: production-never-uses-dev-dependencies
  comment: "A devDependency is absent from a production install. plan:0005-guard-catalogue"
  fix: "Move the package to dependencies in package.json, or move the import into test or build code."
  severity: error
  from: { path: "^src/", pathNot: ["\\.(test|spec)\\.[jt]sx?$", "(^|/)__tests__/"] }
  to:   { dependencyTypes: [npm-dev], dependencyTypesNot: [type-only] }

No copyleft licence reaches the product

forbiddenerrorwave 1

license matches the package's declared licence, as dependency-cruiser reads it. Pair it with the recommended rule against packages missing from package.json.

rules.dependencies.forbidden[]
- name: no-copyleft-in-product
  comment: "The product is distributed under MIT; a copyleft dependency changes that. adr:0019"
  fix: "Replace the package with an MIT, BSD or Apache-2.0 alternative, or keep it in tooling that is never shipped."
  severity: error
  from: { path: "^(apps|packages)/", pathNot: "^packages/tooling/" }
  to:   { license: "(GPL|AGPL|LGPL|SSPL)" }

Coupling: stable code on unstable code, hubs, and shared code with one user

forbiddenwarnwave 1

Instability is the outgoing share of a module's edges. moreUnstable flags a module that depends on something less stable than itself. Dependents rules match on the module key and count who imports it.

rules.dependencies.forbidden[]
- name: stable-never-depends-on-unstable
  comment: "A stable package pulled toward an unstable one inherits its churn. plan:0005-guard-catalogue"
  fix: "Invert the edge behind an interface in the stable package, or move the volatile code up."
  severity: warn
  from: { path: "^packages/(core|domain)/" }
  to:   { moreUnstable: true, dependencyTypesNot: [type-only] }

- name: no-hub-modules
  comment: "A module with more than 40 dependents is a hidden global. plan:0005-guard-catalogue"
  fix: "Split the module by the concerns its importers use; a barrel file that re-exports everything is the usual cause."
  severity: warn
  module: { path: "^src/", pathNot: "(^|/)index\\.ts$", numberOfDependentsMoreThan: 40 }

- name: shared-means-shared
  comment: "Code under shared/ with one importer belongs beside that importer. plan:0005-guard-catalogue"
  fix: "Move the module into the folder of its only importer, or delete it."
  severity: warn
  module: { path: "^src/shared/", numberOfDependentsLessThan: 2 }

Convention guards

Where code may live and what it may know about. The shorthands exist because most dependency-cruiser configs write a layer model out longhand as five or six rules; rulebearing config expand prints the expansion so nothing is hidden.

Layers: a lower layer never depends on a higher one

shorthanderrorwave 1

Listed highest to lowest. Each lower layer gets one forbidden rule per higher layer, named clean:domain-to-web and so on, all sharing the fix.

rules.layers[]
- name: clean
  comment: "Clean architecture: web calls application, application calls domain, never the reverse. plan:0005-guard-catalogue"
  fix: "Depend inward. Put the interface in the lower layer and the implementation in the higher one."
  severity: error
  layers:
    - "^src/web/"
    - "^src/application/"
    - "^src/domain/"

Independence: features and apps do not import each other

shorthanderrorwave 1

The pattern has exactly one capturing group naming the unit. It expands to one $1 fence: files under one feature may not import another feature. The longhand form is shown for the cases the shorthand cannot express, here with an exception list from JSON.

rules.independence[] and the longhand
rules:
  independence:
    - name: features-are-independent
      comment: "A feature talks to another feature through packages/, never by import. plan:0005-guard-catalogue"
      fix: "Move the shared code into packages/, or expose it from the feature's public API and register it there."
      pattern: "^apps/web/src/features/([^/]+)/"

  dependencies:
    forbidden:
      - name: no-app-to-app
        comment: "Apps share only packages/* and HTTP; the legacy apps are exempt until their split lands. plan:0005-guard-catalogue"
        fix: "Call the other app over its API, or move the shared code into packages/."
        severity: error
        from: { path: "^apps/([^/]+)/", pathNot: "^apps/(${legacyApps})/" }
        to:   { path: "^apps/([^/]+)/", pathNot: "^apps/$1/" }
        examples:
          forbidden: ["apps/web/src/a.ts -> apps/admin/src/b.ts"]
          allowed:   ["apps/web/src/a.ts -> apps/web/src/b.ts"]

defines:
  legacyApps: { fromJson: eng/legacy-apps.json, select: "apps[*].name" }   # joined with | by default

Imports into a package go through its public entry point

forbiddenerrorwave 1

Lookaround is refused by the linear-time engine, so the exclusion is a pathNot, not a negative lookahead. The capture keeps a package's own internal imports legal.

rules.dependencies.forbidden[]
- name: packages-are-entered-through-index
  comment: "A package's public API is its src/index.ts; deep imports freeze its file layout. plan:0005-guard-catalogue"
  fix: "Export the symbol from the package's src/index.ts and import it from the package name."
  severity: error
  from: { path: "^(apps|packages)/([^/]+)/" }
  to:
    path: "^packages/([^/]+)/src/"
    pathNot:
      - "^packages/$2/"                        # a package may import its own files
      - "^packages/[^/]+/src/index\\.ts$"      # the public entry point
  examples:
    forbidden: ["apps/web/src/page.tsx -> packages/ui/src/button/button.tsx"]
    allowed:
      - "apps/web/src/page.tsx -> packages/ui/src/index.ts"
      - "packages/ui/src/index.ts -> packages/ui/src/button/button.tsx"

- name: ui-never-imports-server
  comment: "Client components must not bundle server code or secrets. plan:0005-guard-catalogue"
  fix: "Call the server through a route handler or a server action; import only types from the server tree."
  severity: error
  from: { path: "^apps/([^/]+)/src/(components|app/.*/client)/" }
  to:   { path: "^apps/$1/src/server/", dependencyTypesNot: [type-only] }

Must-reach: every route handler reaches the auth check

requirederrorwave 1

A required rule flags a module matching module that does not import a target. With to.reachable: true it is enough to reach it through any chain, which is how a handler that wraps its own middleware still passes.

rules.dependencies.required[]
- name: routes-reach-the-auth-guard
  comment: "Every API route is authenticated; an unguarded route is the one that leaks. plan:0005-guard-catalogue"
  fix: "Wrap the handler in withAuth from src/server/auth/guard.ts, or import a middleware that does."
  module: { path: "^apps/web/src/app/api/.*/route\\.ts$", pathNot: "^apps/web/src/app/api/(health|public)/" }
  to:     { path: "^apps/web/src/server/auth/guard\\.ts$", reachable: true }

- name: features-register-their-public-api
  comment: "A feature without an index has no public API to fence. plan:0005-guard-catalogue"
  fix: "Add src/features//index.ts and export the feature's entry points from it."
  module: { path: "^apps/web/src/features/([^/]+)/[^/]+\\.tsx?$", pathNot: "index\\.ts$" }
  to:     { path: "^apps/web/src/features/$1/index\\.ts$", reachable: true }

Naming, visibility and shape: element rules

elementserrorwave 2

ArchUnitNET's selectors, predicates and conditions as declarative keys in camelCase. select.kind is one of type, class, interface, attribute, member, field, method, property, function, module. all, any and not combine predicates. A predicate the language cannot answer is exit 3, never a silent pass.

rules.elements[]
- name: handlers-are-internal-and-sealed
  comment: "A handler is reached through MediatR, never referenced directly. plan:0005-guard-catalogue"
  fix: "Mark the handler internal sealed. Nothing outside the Application project may name it."
  select:
    kind: class
    where:
      all:
        - haveNameEndingWith: Handler
        - resideInNamespaceMatching: "^Shop\\.Application\\."
        - not: { areAbstract: true }
  should: { all: [ { beInternal: true }, { beSealed: true } ] }
  because: "A handler is an implementation detail of the Application project."

- name: controllers-are-named-and-placed
  comment: "A controller outside Web.Controllers is not picked up by the route convention. plan:0005-guard-catalogue"
  fix: "Rename the class to end in Controller and move it under Shop.Web.Controllers."
  select: { kind: class, where: { areAssignableTo: "Microsoft.AspNetCore.Mvc.ControllerBase" } }
  should:
    all:
      - haveNameEndingWith: Controller
      - resideInNamespaceMatching: "^Shop\\.Web\\.Controllers"

- name: endpoints-do-not-return-http-response-message
  comment: "HttpResponseMessage bypasses the result filters. plan:0005-guard-catalogue"
  fix: "Return IResult or ActionResult and let the filters shape the response."
  select:
    kind: method
    where: { all: [ { declaredInTypesThat: { resideInNamespaceMatching: "^Shop\\.Web\\.Endpoints" } }, { arePublic: true } ] }
  should: { notHaveReturnType: ["System.Net.Http.HttpResponseMessage"] }

- name: domain-entities-are-immutable
  comment: "An entity mutated from outside the aggregate skips its invariants. plan:0005-guard-catalogue"
  fix: "Make the setters private or init-only and expose a method that enforces the invariant."
  select: { kind: class, where: { resideInNamespaceMatching: "^Shop\\.Domain\\.Entities" } }
  should: { beImmutable: true }

- name: public-python-functions-are-snake-case
  comment: "PEP 8 names for the public surface of the service. plan:0005-guard-catalogue"
  fix: "Rename the function to snake_case, or prefix it with an underscore if it is private."
  select: { kind: function, where: { all: [ { resideInNamespaceMatching: "^svc\\.api\\." }, { arePublic: true } ] } }
  should: { haveNameMatching: "^[a-z][a-z0-9_]*$" }
Cross-language where the concept exists. kind: class with areSealed is C#. haveAnyAttributes reads decorators in TypeScript and Python. kind: function with arePublic reads export in TypeScript and a leading underscore in Python. The full vocabulary is the ArchUnitNET coverage tab under docs/artifacts/.

Slices: bounded contexts stay apart

sliceserrorwave 2

A slice pattern is a namespace pattern for .NET, a dotted module pattern for Python, and a path pattern for TypeScript. Both conditions are also expressible as dependency rules; the slice form reads as the architecture rather than as a regex.

rules.slices[]
- name: bounded-contexts-do-not-know-each-other
  comment: "Modular monolith: each context owns its data and talks through the shared kernel. plan:0005-guard-catalogue"
  fix: "Publish an event or a shared-kernel interface instead of referencing the other context."
  matching: "Shop.(*)"                 # (**) for MatchingWithPackages
  should: [notDependOnEachOther, beFreeOfCycles]
  ignore: ["Shop.SharedKernel"]

- name: web-features-are-slices
  comment: "The same rule for the TypeScript front end. plan:0005-guard-catalogue"
  fix: "Move the shared code into packages/."
  matching: "apps/web/src/features/(*)/"
  should: notDependOnEachOther

Diagrams: the code matches the component diagram

diagramserrorwave 2

Types match components by the component's <<pattern>> stereotype; any dependency the diagram does not draw is a violation. The plantuml reporter draws the diagram from slices or folders, so it can be generated once and then enforced.

rules.diagrams[]
- name: matches-the-context-diagram
  comment: "docs/architecture/components.puml is the reviewed picture; code follows it. plan:0005-guard-catalogue"
  fix: "Either remove the dependency or change the diagram in the same pull request, with the reason."
  select: { kind: type, where: { resideInAssemblyMatching: "^Shop\\." } }
  adhereTo: docs/architecture/components.puml

Budgets and exceptions

The guards that keep the other guards honest over time. Every one refuses the cheapest path to green: a ceiling cannot be raised, a baseline entry expires, an exception has a date and an owner.

A ratchet: a count that may only fall

ratchetswave 1

Counts the direct edges matching from and to, with $1 captures, and compares with the ceiling in the budget file. An exceeded ratchet is one error. A missing budget is exit 2. count --write lowers the ceiling to the current count and refuses to raise it.

rules.ratchets[] and eng/routes-via-service-budget.json
rules:
  ratchets:
    - name: routes-via-service
      comment: "Route files reach the database through the service layer; the direct edges are being retired. adr:0029"
      fix: "Move the query into apps//src/server/services and call it from the route."
      owner: "@web-platform"
      from: { path: "^apps/([^/]+)/src/app/.*/(page|route)\\.tsx?$" }
      to:   { path: "^apps/$1/src/(server|domain)/" }
      budget: eng/routes-via-service-budget.json

# eng/routes-via-service-budget.json
# { "ceiling": 14 }
#
# rulebearing count --from '^apps/([^/]+)/src/app/.*/(page|route)\.tsx?$' --to '^apps/$1/src/(server|domain)/' \
#   --budget eng/routes-via-service-budget.json --write      # lowers 14 to today's count; a raise is refused

A baseline: accept today's findings, each with a deadline

knownViolationswave 1

rulebearing adopt writes this on a brownfield repository so the first run is green. A known finding is reported with severity ignore. An entry past its date fails the run the day after, so the baseline shrinks or someone renews it by name.

options.knownViolations[]
options:
  knownViolations:
    - id: RB-4f2a9c10                       # stable: rule, both ends and the kind of edge
      rule: { name: ui-never-imports-server, severity: error }
      expires: 2026-12-31
      owner: "@orders-team"
    - from: apps/web/src/app/orders/page.tsx  # dependency-cruiser's own shape is accepted as it is
      to: apps/web/src/server/db.ts
      rule: { name: ui-never-imports-server, severity: error }

A temporary rule, an exception list, and a rule ahead of its first match

metadatawave 1

Three ways to record an exception without weakening the fence. expires puts a date on a temporary rule. defines keeps the exception list in a JSON file with an owner and a review, out of the regex. allowEmpty excuses one rule from liveness by name.

rulebearing.yaml
defines:
  migratingPackages: { fromJson: eng/migration.json, select: "packages[*]", joinWith: "|" }

rules:
  dependencies:
    forbidden:
      - name: no-legacy-http-client-except-migrating
        comment: "The legacy client is retired by the end of Q4 2026. plan:http-client-migration"
        fix: "Use packages/http; add the package to eng/migration.json only with the owner's review."
        severity: error
        from: { path: "^packages/", pathNot: "^packages/(${migratingPackages})/" }
        to:   { path: "^packages/legacy-http/" }
        owner: "@web-platform"
        expires: 2026-12-31                # the run fails on 2027-01-01 if the rule is still here

      - name: plugins-stay-apart
        comment: "Plugins are independent; the first one lands next sprint. plan:plugin-host"
        fix: "Talk to another plugin through the host API."
        severity: error
        from: { path: "^plugins/([^/]+)/" }
        to:   { path: "^plugins/([^/]+)/", pathNot: "^plugins/$1/" }
        allowEmpty: true                   # matches nothing until plugins/ has two entries

# For a rule that lives in an extended .dependency-cruiser.* file, which cannot carry the key:
# allowEmpty: [plugins-stay-apart]
What the engine will not let a rule do. Raise a ceiling with count --write. Pass while matching nothing. Merge without a decision token when --require-comment-token is on. Use lookaround in a pattern. Return a silent false for a predicate the language cannot answer. Each is a failure, not a warning.

Prove the rule

A rule is code. These commands are its tests, its linter and its documentation.

CommandAnswers
rulebearing testDoes each rule flag its examples.forbidden edges and pass its examples.allowed ones, on a synthetic graph built from them?
rulebearing config lint --graph .graph/cruise.jsonCan a rule never match? Is it shadowed by an earlier one? Does an allowed list admit everything? Is a fix missing or a restatement of the name? Is a decision token missing?
rulebearing explain <rule>The rule in a sentence, its reason and fix, what each side matches today, and the first edges it flags.
rulebearing rules --jsonEvery rule with its family, severity and how many modules each side matched. A zero on the from side is the vacuous rule liveness will fail.
rulebearing can-import <from> <to>Yes or no, with the rule that decides it, from the cached graph, before the import is written.
rulebearing propose --from <glob> --to <glob>A draft rule with the match counts on both sides and the edges it would flag today. --from-example "a.ts -> b.ts" generalises one edge to the narrowest rule that covers it. Wave 2.
rulebearing cruise --require-comment-token -T err-longThe gate itself. Every finding prints the rule's fix; the exit code is the count of error findings.

Before you merge a rule

  • The comment says why and carries adr:NNNN or plan:<slug>.
  • The fix is an imperative someone can follow without opening the rule.
  • examples.forbidden and examples.allowed are present and rulebearing test is green.
  • rulebearing rules --json shows a non-zero match on the from side, or the rule is named in allowEmpty with the reason in its comment.
  • rulebearing config lint reports no shadowing and no never-matching pattern.
  • A temporary rule or baseline entry has owner and expires.
  • No ratchet ceiling was raised. No pathNot was widened to get green without a decision recorded.
  • The rule uses pathNot rather than lookaround, and captures rather than duplicated literals.
